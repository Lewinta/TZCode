# HRMS `salary_slip.py` Explained (For New Developers)

This guide explains how `hrms/hrms/payroll/doctype/salary_slip/salary_slip.py` works, what happens during Salary Slip generation, and where to customize behavior safely from a custom app like `tzcode`.

---

## 1) What this file is responsible for

The HRMS `SalarySlip` class is the core payroll calculator for one employee and one payroll period.

It handles:

- Validation (employee active, dates, duplicates, structure assignment)
- Working days, LWP, attendance, timesheet logic
- Earnings and deductions component calculation
- Additional Salary integration
- Tax slab and variable tax deductions
- Loan repayments
- YTD/MTD aggregations
- Submit/cancel side effects (status updates, emails, loan entries)

In short: this file is both the **orchestration layer** and the **calculation engine** for payroll slips.

---

## 2) Important imports and dependencies

`salary_slip.py` depends on many HRMS/ERPNext utilities:

- Payroll period helpers (`get_payroll_period`, `get_period_factor`)
- Additional Salary query helper (`get_additional_salaries`)
- Benefit/claim helpers (`get_benefit_component_amount`, `get_benefit_claim_amount`)
- Loan helpers (`set_loan_repayment`, `make_loan_repayment_entry`, `cancel_loan_repayment_entry`)
- Safe formula processing (`sanitize_expression`, `_safe_eval`)
- Frappe query builder for historical totals and aggregations

Because of this, changing one part of payroll often affects tax, benefits, and net pay calculations.

---

## 3) Main class and lifecycle

`class SalarySlip(TransactionBase)` is the main doctype class.

### Key lifecycle methods

- `validate()`
  - Main pre-save pipeline.
  - Calls validation + working-day setup + salary computation + YTD/MTD.
- `on_submit()`
  - Prevents negative net pay.
  - Creates loan repayment entries.
  - Optionally emails salary slip.
- `on_cancel()`
  - Reverts status/loan repayment effects.

### Key cached properties

- `joining_date`, `relieving_date`
- `payroll_period`
- `actual_start_date`, `actual_end_date` (adjusted for join/relieve within period)

These properties avoid repeated DB calls and align calculations with employee tenure.

---

## 4) High-level flow of Salary Slip calculation

This is the practical order for most non-timesheet slips:

1. `validate()`
2. `get_date_details()` / `get_emp_and_working_day_details()`
3. `set_salary_structure_assignement()`
4. `calculate_net_pay()`
5. `compute_year_to_date()` + `compute_month_to_date()` + component-wise YTD

Inside `calculate_net_pay()`:

1. `calculate_component_amounts("earnings")`
2. Compute `gross_pay`
3. `calculate_component_amounts("deductions")`
4. `set_loan_repayment(self)`
5. `set_precision_for_component_amounts()`
6. `set_net_pay()`
7. `compute_income_tax_breakup()`

This order matters because deduction formulas can depend on earnings and additional components populated earlier.

---

## 5) How earnings/deductions are built

`calculate_component_amounts(component_type)` does four major things:

1. Loads salary structure doc
2. `add_structure_components(component_type)`
3. `add_additional_salary_components(component_type)`
4. If deductions: `add_tax_components()`
   If earnings: `add_employee_benefits()`

### Structure components

`add_structure_components()` loops salary structure rows:

- Evaluates row condition/formula via `eval_condition_and_formula()`
- Adds/updates component row using `update_component_row()`
- Supports payment-day dependent amounts
- Skips statistical components from final rows but keeps values in eval context

### Additional Salary components

`add_additional_salary_components()` fetches entries from `Additional Salary` matching:

- employee
- period/date filters
- component type (`Earning` or `Deduction`)

Then each entry is applied with `update_component_row()`.

### Tax components

`add_tax_components()` handles components marked `variable_based_on_taxable_salary`, then computes tax from slabs/history and updates deduction rows.

---

## 6) Formula evaluation context (`data` / `default_data`)

Formulas use context generated by `get_data_for_eval()`:

- Employee fields
- Salary Structure Assignment fields
- Current Salary Slip fields
- All salary component abbreviations initialized to `0`
- Current component row amounts

Then formulas are evaluated in `eval_condition_and_formula()` using sanitized expressions and `_safe_eval`.

`whitelisted_globals` restrict available functions in expressions (`int`, `float`, `round`, `date`, `ceil`, etc.).

---

## 7) Tax computation model

Tax logic is split across:

- `compute_taxable_earnings_for_year()`
- `compute_current_and_future_taxable_earnings()`
- `compute_income_tax_breakup()`
- `calculate_variable_tax()`

Conceptually, it calculates:

- Past taxable earnings/tax paid
- Current period taxable earnings
- Future projected taxable earnings for remaining periods
- Exemptions, additional income, benefit adjustments
- Final variable deduction rows for tax components

This is why tax behavior can change if earnings/deductions context is wrong.

---

## 8) Net pay and totals

`set_net_pay()` computes:

- `total_deduction`
- `net_pay = gross_pay - total_deduction - loan_repayment`
- rounded totals and base-currency values
- amount-in-words text

Helper totals are pulled by `get_component_totals(component_type, depends_on_payment_days=...)`.

---

## 9) Historical/YTD/MTD aggregation

The class computes:

- Year-to-date totals (`compute_year_to_date`)
- Month-to-date totals (`compute_month_to_date`)
- Component-wise YTD (`compute_component_wise_year_to_date`)

It uses salary slip history queries via query builder methods like `get_salary_slip_details()`.

---

## 10) Common extension points (safe customization strategy)

Since this is core HRMS logic, avoid editing this file directly in production. Prefer custom app overrides:

- `override_doctype_class` in `tzcode/hooks.py`
- Subclass HRMS `SalarySlip` and override focused methods

Good override targets:

- `get_data_for_eval()` (formula context rules)
- `add_additional_salary_components()` (custom fetching or merge rules)
- `update_component_row()` (merge/overwrite behavior)
- `compute_income_tax_breakup()` (policy-level tax tweaks)

This keeps upgrades safer and makes diffs easier to maintain.

---

## 11) Known pitfall relevant to Additional Salary

When multiple component rows share the same abbreviation (for example base structure row + Additional Salary row), formula context can be wrong if values are overwritten instead of aggregated.

If deductions are formula-driven and reference that abbreviation, deductions may appear to ignore Additional Salary.

Your `tzcode` override in `tzcode/controllers/overrides/salary_slip.py` addresses this by aggregating duplicate abbreviation values in `get_data_for_eval()`.

---

## 12) Suggested onboarding path for new developers

If you are new to payroll logic, read methods in this order:

1. `validate()`
2. `calculate_net_pay()`
3. `calculate_component_amounts()`
4. `add_structure_components()` + `update_component_row()`
5. `get_data_for_eval()` + `eval_condition_and_formula()`
6. `add_additional_salary_components()`
7. `add_tax_components()` + `compute_income_tax_breakup()`
8. `set_net_pay()`

This sequence gives the clearest mental model of how amounts are built and finalized.
